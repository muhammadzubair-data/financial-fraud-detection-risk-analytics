# Data Dictionary — Financial Fraud Detection & Transaction Risk Analytics

All tables live in `data/raw/*.parquet`. Generated by scripts in `src/data_generation/`,
seeded (SEED=42) for full reproducibility. Scale is controlled by `SCALE` in
`src/data_generation/config.py` (`dev` for fast local iteration, `full` for the
1-2M customer / 5-10M transaction portfolio scale).

## customers.parquet
| column | type | notes |
|---|---|---|
| customer_id | int | primary key |
| signup_date_days_ago | int | tenure at generation end date |
| account_age_days | int | |
| risk_segment | str | latent (`low`/`medium`/`high`) — NOT a real-world observable field, drives fraud likelihood upstream only |
| home_country | str | ISO-ish country code |
| home_state | str | US only, else `N/A` |
| avg_monthly_spend | float | lognormal-distributed baseline spend |
| is_frequent_traveler | bool | explains legitimate geographic anomalies |
| date_of_birth_year | int | |

## accounts.parquet
| account_id | customer_id | account_type (`primary`/`savings`/`credit`) | account_age_days | account_status |

## devices.parquet
| device_id | customer_id | device_type | first_seen_days_ago | is_shared_device |
Note: `is_shared_device=True` rows mean the same `device_id` appears under more
than one `customer_id` — a fraud-ring / account-takeover signal.

## merchants.parquet
| merchant_id | merchant_category | merchant_country | merchant_risk_score | merchant_age_days | is_high_risk_outlier |

## transactions.parquet  (the core fact table)
| column | type | notes |
|---|---|---|
| transaction_id | int | primary key, chronologically ordered |
| customer_id | int | FK → customers |
| merchant_id | int | FK → merchants |
| device_id | int, nullable | FK → devices; null when device_id_raw is a synthetic takeover device string |
| device_id_raw | str | always populated; use this for device-sharing/velocity features |
| timestamp | datetime | |
| amount | float | |
| txn_country | str | |
| txn_lat / txn_lon | float | jittered around country centroid |
| distance_from_prev_km | float | haversine distance from customer's previous transaction location |
| new_device_flag | bool | device differs from customer's last-used device |
| failed_attempts_24h | int | simulated declined-then-approved pattern |
| is_fraud | bool | **target label** |
| _reason_codes | str | comma-separated ground-truth signal list, POPULATED ONLY WHEN is_fraud=True. Kept for EDA/validation only — never use as a model feature (pure leakage, it's generation metadata, not something known at transaction time in reality). |

## chargebacks.parquet
| chargeback_id | transaction_id | chargeback_date | chargeback_reason | chargeback_amount | is_fraud_related |
~72% of true fraud eventually gets disputed (detection lag modeled by
1-75 day gap); ~0.4% of legitimate transactions also get disputed for
non-fraud reasons (product/duplicate/subscription disputes).

## investigations.parquet
Represents a **historical, naive rule-based** review queue (amount threshold +
new device + failed attempts + distance), capped at ~60 reviews/day to model
a fixed analyst capacity constraint. This is the baseline the project's
ML-driven "Expected Fraud Loss" investigation ranking is designed to beat.

| investigation_id | transaction_id | flagged_date | flag_score | outcome | resolution_time_hours |

`outcome` ∈ `confirmed_fraud`, `false_positive_cleared`, `false_negative_cleared`
(rare analyst miss recorded post-hoc).

## transactions_features.parquet (data/processed/, output of src/features/build_features.py)
All columns above, plus point-in-time engineered features (see module
docstring for the causal/leakage-safe construction rule):

| column | type | description |
|---|---|---|
| txns_last_1h / txns_last_24h | int | count of this customer's PRIOR transactions in the trailing window |
| amount_vs_customer_avg | float | this amount ÷ customer's expanding mean amount (prior txns only) |
| customer_amount_zscore | float | (amount - prior mean) / prior std, prior txns only |
| time_since_last_txn_sec | float | seconds since this customer's previous transaction (-1 if first) |
| is_first_txn | int | 1 if this is the customer's first observed transaction |
| device_accounts_count | int | distinct customers ever linked to this device_id |
| is_shared_device | int | device_accounts_count > 1 |
| home_country, avg_monthly_spend, is_frequent_traveler, account_age_days | — | joined from customers (static, known-in-advance attributes) |
| merchant_category, merchant_risk_score, is_high_risk_outlier | — | joined from merchants |
| is_cross_border | int | txn_country != customer's home_country |
| hour_of_day, day_of_week, is_night_txn, amount_log | — | derived time/amount transforms |

`risk_segment` is deliberately EXCLUDED from the feature set — it's the
latent variable used to generate fraud probability during data creation
and would be a direct label proxy, not something a real fraud team
observes.

## Known leakage traps intentionally NOT present
- No column reveals `is_fraud` indirectly (e.g. no "flagged_by_bank" column on transactions itself).
- `_reason_codes` is clearly marked as generation-only metadata.
- All behavioral features (rolling averages, velocity, distance) must be
  engineered downstream using ONLY prior-in-time transactions — see
  `src/features/` — the raw table does not pre-compute point-in-time
  features for you on purpose.
